# mdm-customer · 使用手册

## 1. 项目结构

```
mdm-customer/
├── component.yaml                        # 平台读的那份
├── assembly.yaml                         # 只有 be-ops 读
├── contracts/
│   ├── mdm/customer/v1/customer.proto    # gRPC 契约
│   ├── customer.openapi.yaml             # HTTP 契约（对外 REST）
│   └── events/customer.events.json       # 事件 schema（只增不删不改，决策 19）
├── backend/
│   ├── module/module.go                  # 唯一入口 New(ctx, rt)，单跑与合并共用
│   ├── cmd/
│   │   ├── server/main.go                # 一行 besdk.RunStandalone(module.New)
│   │   └── migrate/main.go                # 全拆态迁移容器入口（合并态由外壳读 Module.Migrations）
│   └── internal/
│       ├── repo/       # 数据访问层：customers/contacts/billing_infos + Outbox 写入
│       ├── service/    # 业务规则层：入参校验、错误码映射，repo/grpc/http 的共用入口
│       ├── http/       # REST：/mdm/customer/**
│       ├── grpc/       # gRPC：mdm.customer.v1.CustomerService
│       └── partition/  # 后台循环：event_outbox/event_inbox 未来分区自动创建
├── migrations/
│   ├── embed.go                          # //go:embed *.sql（Go 的 embed 不许 ".."，只能与 .sql 同目录）
│   ├── 001_create_customers.{up,down}.sql
│   └── 002_create_outbox_inbox.{up,down}.sql
├── Dockerfile
├── Makefile
└── README.md
```

（详见总纲 §4 SOP-B 的标准布局。SOP-P 判过：本组件是只读枢纽 + 常规 CRUD，不用任何设计模式——`repo`/`service`/`http`/`grpc` 四层直给，没有额外的抽象层）

## 2. 功能详解

| 功能 | rpc / 路径 | 要点 |
|---|---|---|
| 建档 | `Create` / `POST /mdm/customer/customers` | **幂等键怎么构造**：调用方自己生成一个全局唯一的 `idempotency_key`（建议 UUID），同一个 key 重复提交返回**同一条已存在的记录**（不报错、不新建，查 `command_idempotency` 表命中即直接返回）。`code` 留空则自动生成 `"C"` + 6 位数字（`nextval('customers_id_seq')`），显式传入则走唯一索引 `customers_code_uniq` 去重 |
| 改档 | `Update` | 幂等键同上；额外带乐观锁 `version`——请求的 `version` 与库里当前值不一致时拒绝（`Aborted`/409），不覆盖并发修改 |
| 启用/停用 | `SetStatus` | 幂等键 + `version` 乐观锁同上。**`DISABLED` 不是终态**：允许流转回 `ACTIVE`（客户后续可能重新建立业务关系）。停用发 `mdm.customer.disabled.v1`；重新启用发 `mdm.customer.updated.v1`（事件清单没有单独的 "enabled" subject，见 §9 决策 19） |
| 联系人 | `AddContact` | 幂等键同上，无对应事件（事件清单没声明这个 subject，不能顺手发明一个） |
| 查单条 | `Get` / `GET /mdm/customer/customers/:id` | 查不到返回 `NotFound`/404 |
| 查列表 | `List` / `GET /mdm/customer/customers` | 游标分页（决策 53，无 `offset`），不传时间范围默认最近 90 天（§11.4.1）；最后一页 `next_cursor` 为空字符串，不是报错 |
| 批量查 | `BatchGet`（只有 gRPC，不暴露 REST） | BFF 层防 N+1 的唯一合法调用方式（§3.8）。缺失的 id 进 `missing_ids`，不报错 |
| 摘要投影 | `GetSummary` | 给列表/摘要场景用的轻量字段集，减少跨组件同步摘要副本时的 payload |

## 3. 完整契约清单

**gRPC `mdm.customer.v1.CustomerService`**（`contracts/mdm/customer/v1/customer.proto`）：`Create`、`Update`、`SetStatus`、`AddContact`、`Get`、`List`、`BatchGet`、`GetSummary`——8 个 rpc，`buf lint`/`buf breaking` 守着不出破坏性变更。

**REST**（`contracts/customer.openapi.yaml`，前缀 `/mdm/customer/**`）：`POST /customers`、`PATCH /customers/:id`、`POST /customers/:id/status`、`POST /customers/:id/contacts`、`GET /customers/:id`、`GET /customers`。`BatchGet` 不暴露到 REST（§3.8：它是给其他组件 gRPC 客户端用的，不是终端用户操作）。`/healthz`/`/metrics` 由 `besdk.NewGinEngine` 统一挂，本组件不重复注册。

**事件**（`contracts/events/customer.events.json`，全部走 Outbox）：`mdm.customer.created.v1`、`mdm.customer.updated.v1`、`mdm.customer.disabled.v1`。Schema 演进铁律：只增不删不改（决策 19），下游按 `version` 单向递增更新摘要副本。

## 4. 数据模型

不贴完整 DDL——那在 `migrations/*.sql` 里，贴一份必然过期。要点：

| 表 | 分区 | 归档 | 说明 |
|---|---|---|---|
| `customers` | 不分区 | 不归档 | 主表，`code` 唯一索引，`credit_limit NUMERIC(18,2)` |
| `contacts` | 不分区 | 不归档 | 外键 `customer_id → customers.id` |
| `billing_infos` | 不分区 | 不归档 | 外键 `customer_id → customers.id` |
| `event_outbox` / `event_inbox` | **按周分区**（`decision 54`：跨周不建分区会写崩，`partition` 包每天检查一次并提前建好未来 4 周） | 不归档（表本身不是主数据，但没有归档流程，靠分区自然滚动） | `PRIMARY KEY (id, created_at)` 含分区键；owner 是 `mdm_customer_rw`（`ALTER TABLE ... OWNER TO`，分区维护要建新分区，DML 权限不够，见 A4f） |
| `command_idempotency` | 不分区 | 不归档 | `idempotency_key TEXT PRIMARY KEY`，所有写接口幂等去重的唯一真相源 |

`customers`/`contacts`/`billing_infos` 为什么不分区不归档：设计计划 §7——这三张表是主数据（公司数量级，几千到几万行），不是交易流水，§11.2.5 的分区大表清单里没有 `mdm-*`。

## 5. 开发

```bash
cd components/mdm/customer
go test ./... -race -count=1         # 需要 TEST_PG_DSN（真库，不 mock）与 TEST_NATS_URL（可选）
make all                              # 8 个门禁（check-version/test/image/migrate-idempotent/
                                       # dag-check/contract-check/import-scan/module-check）
make smoke                            # 单独跑：只装这一个组件能不能 brickkit up 起来
```

改契约（`contracts/mdm/customer/v1/customer.proto`）后：`buf lint && buf generate`，`gen/` 目录是生成产物，不手改。改了字段/rpc 要过 `make contract-check`（`buf breaking`）——只许向后兼容地追加，不许删字段/改类型/改 tag 编号（§3.4 铁律 3）。

改迁移：新增 `NNN_xxx.up.sql`/`.down.sql`，不改已发布的旧迁移文件；分区表（`event_outbox`/`event_inbox`）改结构要连着分区一起想（新分区继承父表结构，改父表不会自动改已建好的旧分区）。

## 6. 排障

| 症状 | 根因 | 怎么办 |
|---|---|---|
| 容器一直 `unhealthy`，日志干净 | `wget --spider`（平台健康检查）发 HEAD，`/healthz` 只注册过 GET | 已在 `be-sdk-go` v0.1.5 修（`engine.HEAD`），确认依赖版本 ≥ v0.1.5 |
| 容器一直 `unhealthy`，日志有 panic | `rt.Tracer`/`rt.Meter` 是 nil interface | 已在 `be-sdk-go` v0.1.4 修，确认依赖版本 ≥ v0.1.4 |
| `docker stop` 掉 postgres 后容器进入重启死循环 | outbox pump 单轮查询失败被当硬错误上抛，`Start()` 返回 error 让整个进程退出 | 已在 `be-sdk-go` v0.1.6 修（失败只记日志，循环继续），确认依赖版本 ≥ v0.1.6 |
| `grpcurl localhost:9090` 连不上 | gRPC 额外端口没有宿主机映射（`expose`/`exposePort` 只映射主端口） | 用容器的 Docker 网络 IP：`docker inspect <容器名> --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'` |
| 迁移报 `must be owner of table event_outbox` | 分区维护用 `mdm_customer_rw` 建分区，但表是迁移用的管理凭据建的，owner 没变过 | 迁移里对会被运行时代码分区的表显式 `ALTER TABLE ... OWNER TO mdm_customer_rw` |

更完整的实测记录（含根因分析与最小复现）见装配仓库根 `docs/dev/实测踩坑记录.md` 的 A4 系列条目。
